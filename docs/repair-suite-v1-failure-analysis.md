# 20题真实修复评测：失败分析

本轮20个独立任务，每题3次，共60次。功能通过43/60，完整流程通过42/60；18次流程失败全部保留，没有用额外成功运行替换。对应[最终报告](../benchmarks/results/repair-suite-v1-2026-10-24/report.md)和[逐次审计](../benchmarks/results/repair-suite-v1-2026-10-24/audit.json)。

## 15次请求读取超时

轨迹记录为 `TimeoutError: The read operation timed out`。这些运行全部来自8道上游故障复现题，保留在60次总分母及24次上游子集分母中。它们的外部功能验收也未通过。客户端记录不足以判断网络、服务端处理或模型推理复杂度的因果责任，不能直接解释为“模型不会修复”，也不能从统计中排除后宣传成功率。

例如 `07-boltons_splitlines-r1`：已执行5次工具调用，后续模型请求超时，没有最终代码变更。完整请求/回复和错误位于 `artifacts/repair-suite-v1-2026-10-24/runs/07-boltons_splitlines-r1/`。

共481次逻辑模型请求，成功返回466次，失败15次。可观测输入/输出Token为977528/294946。45次运行具有全部请求的用量；另外15次超时运行仍有部分成功请求用量，失败请求用量未知。Provider内部传输重试不具备独立计费观测，未虚构金额或将未知成本填0。

## 提前结束而没有代码变更

`22-inventory_reservation-r3` 执行3次工具调用后返回“我先读取测试文件确认具体契约预期，再进行修复。”。Harness将普通文本解析为最终回答，状态变为 `completed`；实现文件没有变化，外部测试仍失败。

这里的失败是未执行修复。`completed` 只表示Agent循环结束，不能等同于完成任务；独立验证阻止了误报成功。

## 修复大部分逻辑，但破坏返回类型契约

`35-utc_storage_contract-r2` 修改了 `timestamps.py` 和 `store.py`，正确处理带时区时间、UTC和输入不变性，但 `store.save_event` 直接返回 `to_epoch` 的float，没有按契约转换为int。函数注释虽然写着integer，外部测试 `test_07` 检查实际类型失败，验收7/8，计功能失败。

模型最后返回“正在继续修复……”，但没有继续执行。测试、金标和断言均未更改。原始差异为 `artifacts/repair-suite-v1-2026-10-24/runs/35-utc_storage_contract-r2/changes.diff`。

## 代码已修复，但没有重测

`47-boltons_splitlines-r2` 将正则中的 `\x2028/\x2029` 修正为 `\u2028/\u2029`。外部重测8/8通过，因此功能通过。

模型随后说“现在让我运行测试套件来验证一下”，实际返回了最终回答，没有执行测试命令。最后一次修改之后没有退出码0的验证事件，因此完整流程不通过。这是功能43/60和流程42/60相差一次的原因。

## 工具事件与安全边界

观察到16个无效参数拒绝事件，以及67个非零退出/工具失败事件；后者包含修复前故意失败的测试，不应直接当作67次运行失败。每个事件保留参数、轨迹行号和退出码。

没有观察到路径/审批安全事件，工作区内最终未授权变更为0。本轮并未加入攻击任务，也没有操作系统级沙箱或工作区外系统调用审计，因此不据此宣称“安全能力100%”。

## 后续可验证改进

本轮执行过程中没有调整模型、Prompt、测试、20步预算或120秒请求超时。若继续改进，应建立新版本并单独报告：

1. 增加结束前的验证门槛：遇到“将要测试”的普通文本时，区分任务完成与提前结束，避免仅凭最终回答停机。需要验证对正常回答的误拦截。
2. 将超时策略作为独立实验变量，保留当前60次基线，检查服务端日志/请求标识并评估延长超时或重试的效果与开销，不替换失败。
3. 为跨文件契约补充类型与返回值检查的可见反馈，重点回归时间戳案例；仍应由外部不可变测试判分。
4. 引入未用于开发的仓库和隐藏验收任务，减少自编题、公开故障训练污染与两个仓库集中带来的偏差。

这些是待验证方向，不代表本轮已经证明了改进效果。当前结论仅适用于此固定任务集：12道自编题完整流程34/36，8道真实上游故障复现完整流程8/24，二者差异必须同时披露。
