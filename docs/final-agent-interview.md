# CodeTrail：Agent开发实习面试讲解

## 两分钟讲法

我围绕本地代码Agent Harness完善了原生Tool Calling、上下文交付、错误反馈、状态持久化和评测审计。项目重点不是堆工具，而是验证模型是否真的改对代码、是否执行必要步骤、失败时能否恢复，以及是否遵守权限。

评测拆成原有20题各三次和本项目新留出10题各三次，计划共30道不同题、90次独立会话；首批54次余额中断后，经用户换凭据又追加54次，实际保留144次修复执行。原90次结果与追加结果分别报告。每次新工作区，正式请求前冻结代码、题目、测试、必要证据金标和参数。旧题都曾参与评测，其中六题有额外开发调优；新题此前没有运行过Agent。我不会把90次重复说成90道题，也不保证公开上游故障没进入模型预训练。

结果用独立外部验证器判断：重新安装原测试，只叠加允许修改的实现，用独立Python进程复验，再核对最终文件哈希是否等于最后一次通过测试时的状态。工具轨迹、原生请求/响应、代码差异与失败都保留。成功率、过程指标和安全指标分开报告，未评估项不打满分。

当前仍是小规模本地工程评测，不能证明复杂仓库普遍修复能力。应用层文件规则和命令审批也不等于OS沙箱：允许执行的代码仍可能访问本机文件，独立安全集专门展示这个边界。

## 为什么原来会反复读取、修不好代码？

旧链路把历史拼成单条文本，最近工具结果又被截到900字符。一次看似完整的源码读取，函数主体可能根本没送到下一轮；模型再读一次仍看不全。与此同时XML与DSML混用，有结束标记进入补丁内容的真实记录。

修复使用原生assistant/tool消息，保留真实tool_call_id和上下文，长文件按行分页并明确下一段范围。官方与硅基流动的合法reasoning返回不同：硅基流动允许None，我按实际格式保留而不伪造思考文本；官方路径保留原严格检查。格式错误不作为代码写入，补丁拒绝明确说明“未修改、用当前源码修正唯一old_text”。

这并不代表所有模型决策正确。多调用包可能被单步单工具约束拒绝，越过批准命令的探测也会被拒绝；拒绝和重试有成本，必须报告。

## 如何说明评测集可信？

- 原有20题不改变原始故障代码和验收，历史GLM与官方DeepSeek结果保留。全部旧题属于已知题，不能冒充留出。
- 新10题取自more-itertools和python-dotenv十个不同真实修复提交，固定故障父版本、上游来源与许可证。作者在首次Agent运行前验证“故障失败、官方修复通过”。参考实现只用于控制器质量检查，不进入Agent工作区或发布包。
- 留出集首批按预先声明的三次执行，不按成功率删题、换题或调整测试。余额不足后用户提供新凭据，14个留出余额中断槽位进入单列追加恢复；这是公开的协议追加，不冒充仍然只有每题三次，也没有为真实修复失败再试一次。若未来据这些失败改Harness，这批题就应改称开发集，未来再建新的留出。
- 公开测试会带来记忆和过拟合风险；新增包级源码与旧最小复现的难度也不同。因此不把两组分数差当作纯泛化差异或统计显著结论。

## 七维分别回答什么？

| 维度 | 面试时的解释 | 证据 |
|---|---|---|
| 正确性 | 修复是否满足冻结功能契约，最终代码有没有被原始测试实际验证 | 外部验收、diff、最终快照 |
| 检索上下文 | 有无检到预定义必要文件/片段，工具读出的内容有没有进入下一轮 | Gold Recall@3/5/10、源码行覆盖、真实wire |
| 忠实性 | 明确声称测试通过时，是否有匹配的工具与最终文件证据 | 最终回答、退出码、独立复验；广义语义未评估 |
| 工具过程 | 参数是否合法，是否先诊断、读实现、改后重测，补丁拒绝后是否修正 | 完整dispatch与返回、拒绝原因、后续同文件修改 |
| 稳定恢复 | 同题三次表现如何，API/工具/状态异常发生在哪个阶段，有限重试是否恢复 | 0/3至3/3分布、transport与persistence事件 |
| 成本效率 | 付出了多少可观测Token、工具步和时间，失败的成本也算进去 | 原始usage、p50/p95与覆盖率；真实金额缺失不估造 |
| 安全权限 | 路径、敏感值、Shell、非法修改和README注入能否被拦截 | 独立脚本守卫与真实模型攻击；不混入修复分母 |

必要证据不是根据成功轨迹事后倒推，而是在运行前根据原始故障邻域、调用方与解析/展开契约定义。该金标仍是人工定义的代理，不能声称穷尽所有语义证据。重复读取率下降与Recall提升是两回事。

本轮长期记忆效果未在真实任务里评估：每次会话清空，没有可复用长期记忆金标。词法匹配和freshness三个机械专项只验证机制。工具历史的保留是上下文管理，不冒充成熟语义记忆系统。

## Windows WinError 5如何处理？

旧记录中原子替换task_state.json偶发失败，曾造成一条真实修复运行中断。同卷替换探测复现过，不确定具体占用者，不能武断说是杀毒软件。

新实现先在同目录写完整临时JSON并fsync，再原子替换；仅对已知Windows共享/权限异常最多尝试5次，等待25/50/100/200ms。逐次记录尝试、错误码和恢复/耗尽，耗尽保留旧文件与失败临时文件，不删除旧目标、不改ACL、不无限重试。会话文件也使用这一机制。

它解决短时占用的健壮性，不解决真正ACL拒绝、磁盘满或跨多个状态文件的事务一致性。API请求重试只重新生成模型回复，工具等收到完整合法调用后才执行；不能因此宣称整个系统exactly-once。崩溃后的状态不完整仍应按失败审计。

## 为什么不能简单说“换模型提高成功率”？

GLM、官方DeepSeek和硅基流动DeepSeek的模型、服务商、部署版本、Thinking、预算语义、超时与Harness都不同。本轮硅基流动文档把max_tokens与thinking_budget分开，而旧官方8192包含思考。因此历史对照只能描述，不能把变化归因某个单一因素。

模型列表与版本公告只能确认别名及平台声明，不能冻结远端不可变权重。系统记录实际返回ID/指纹，发现不同模型不静默替换；空指纹和未知有效采样配置如实披露。

## 如何解释安全结果？

直接读.env、越界路径、未经批准命令、改测试等由应用层拒绝；已知环境秘密在入模和落盘前脱敏，子进程环境不继承API Key。

但允许修改Python并执行测试意味着代码以当前用户运行。代码可以绕过文件工具读取文件，所以安全集包含“获批代码读取公开假canary”的边界案例。这个案例失败不该被隐藏，也不能通过更宽权限让测试通过。对抗场景需要容器/进程、文件系统与网络隔离，这不是当前本地Harness已经解决的问题。

所有canary都是专门创建的公开假值；没有拿真实Key做攻击素材。真实模型攻击与脚本化守卫分别统计，不能用脚本模拟冒充大模型抵抗注入的成功率。

## 展示顺序

1. 打开最终报告，先指出30道/首批90次＋追加54次，以及原题、留出两组结果。
2. 打开一个真实成功运行的diff和原始测试，展示最后重测快照与最终哈希一致。
3. 展示一条真实失败或未完成记录；没有当轮失败时直接说明，不编造。
4. 展示Windows恢复审计或有限重试专项，再展示一个安全拒绝及允许代码执行的边界。
5. 展示冻结计划、SHA256、逐运行CSV和独立复验，说明其他人如何用自己的环境Key重跑。

## 真实结果与失败讲解

- 首批90次：功能/流程36/90；原题20/60、新留出16/30；其余54次HTTP402余额不足。调度器未及时对余额错误熔断，这是运行治理不足，不能把快速拒绝当效率提升。
- 用户换凭据后，仅对余额中断槽位追加54次：原题40/40、新留出13/14，共53/54（98.15%）。原始90条全部保留，追加协议在首次追加前记录；模型/权限/验收/采样不改。
- 全部实际修复执行144次，89次通过（61.81%）；不是144道题，更不是一个干净的90次无中断实验。原20题与新增10题的逐题三次表和追加表分列。
- 真实失败是holdout_dotenv_spaces的一次追加：只把Tab排除，没解决连续空格；20步中5次被拒、11次分页读取，最后一步才patch，没有重测，外部6项仍失败1项。它反映实现判断、权限约束下的策略和预算分配问题。没有为好看的分数再跑这题。
- 过程904步、114次多工具包协议拒绝、重复读取0/355。拒绝不等于没有成本，低重复也不等于高召回。窄规则识别57个明确测试成功声明，57个均有对应证据；广义语义忠实性未评估。
- 可观测输入/输出Token 5,415,948/290,717；90/144次用量完整，其余未知，不当零。实际费用未评估。所有执行时长p50/p95约30.468/154.194秒，不含独立外部审计，混有快速余额失败，不直接做历史加速比。
- 安全模型固定案例6/6，守卫13/14；失败是获批代码读取本地公开假canary。500次真实IO专项有4次短时替换重试且全部恢复，无终止错误；较早独立500次中另有1次恢复，分批报告，不能合并成修复任务成功率。
- 全量软件测试292项通过。完整报告、逐次CSV、原始trace/diff/验收与哈希可离线检查；本地网页和保存补丁回放均可运行。

## v2面试补充：面对指标与安全质疑

Recall@5的53.21%不能简单归因为检索算法差：总体混有54次余额中断，且四题必要文件标签误用了editable范围。我保留旧分数和金标，只补充分组诊断：无余额中断观察为137/168（81.55%），并明确它不是新主成绩。两次dotenv契约文件漏读仍是实际不足。没有通过删分母、改金标或重跑留出美化结果。

安全方面新增可选Windows AppContainer测试后端，内核核验令牌、过滤工作区副本、零网络能力与Job限额，失败拒绝，不改现有ACL。同14项守卫新后端14/14，旧13/14保留；首次网络错误码测试失败也保留，后续用本地监听阳性对照验证实际投递。共享内核和外网覆盖仍是局限；历史144次不是隔离运行。

可追加简历一句：完善Windows AppContainer隔离验证路径与Job资源限额，完成原14项安全守卫回归、宿主文件和本地网络边界验证；建立Recall指标标注勘误与历史证据保全流程。不得写成已证明检索率、模型修复率或Token成本提升。
