审查日期：2026-11-04。代码基线：`0ff9a8944fc9da0ad5c646e2b8a399ec6e1b8ae1`。

本文件是基于源码与官方技术资料的审查和设计，**不是已实现功能清单或新实验成绩**。本轮没有运行模型、修改冻结题目、改变权限策略或重新计算历史指标。上一轮 340 条自动化测试和 12 项离线机制检查是已有证据；尚不能证明真实模型的长期任务收益。

后续已按用户确认实施小规模完整工作台，当前功能与验证见[实施指南](workbench-v2.md)和[验证报告](../validation/workbench-v2-2026-11-04/report.md)。以下差距与阶段目标保留为上述基线提交的审查快照，不能当作实施后的当前状态。

## 1. 项目定位与验收范围

建议定位：**面向持续演化代码仓库的、可验证的本地代码 Agent Harness**。

主要用户场景：开发者在同一仓库中跨会话修复问题、调整接口、升级依赖；期间源码和环境发生变化，Agent 需要复用有效经验、拒绝失效知识、保留执行现场，并用当前版本的实际测试支持结果声明。

“达到主流水准”在本项目中指选定场景内的核心闭环具备完整的状态、权限、错误、取消、恢复和验证语义。功能规模可以小，基础语义不能靠演示脚本补齐。功能清单相似不意味着模型表现、生态或产品成熟度相同。

现阶段判断：已有真实修复、独立验收、工具审计和 Windows 隔离证据，是可运行的工程原型；长任务、经验复用和交互控制尚未形成经真实模型验证的整体能力。

## 2. 从主流实现中提炼的原则

1. **规则、记忆、上下文各有职责。** Claude Code 区分用户维护的指令和自动记忆，记忆用精简索引导航、详情按需读取。Codex 文档也明确：必须执行的团队要求应写入 AGENTS.md，记忆是召回辅助。这支持长期记忆建设，但不支持“所有主流 Agent 都必须使用同一种向量数据库”的推断。[Claude Code Memory](https://code.claude.com/docs/en/memory)、[Codex Memories](https://learn.chatgpt.com/docs/customization/memories)
2. **会话事实与模型上下文分离。** DeepSeek Harness 以追加事件日志为会话事实源，由日志派生模型消息；Anthropic Managed Agents 将 session、harness、sandbox 分离。这提示我们把多份状态的关系定义清楚，并使压缩后的细节可以按权限重新查回。[DSH Sessions](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/session.md)、[Managed Agents，2026-04-08](https://www.anthropic.com/research/managed-agents)
3. **验证应独立于执行者的自我评价。** Anthropic 的长任务应用开发研究使用独立评价反馈和结构化交接。这支持发展外部验证、任务交接和失败归因；不意味着本项目需要先堆多 Agent 数量。[Harness Design，2026-03-24](https://www.anthropic.com/research/harness-design-long-running-apps)
4. **检索要兼顾符号精确性和语义。** Contextual Retrieval 将带上下文的分块、词法检索、向量召回及可选重排结合。该文章发表于 2024 年，是方法依据，不包装成最新研究；其效果数字不能移植到本项目。[Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)
5. **扩展能力应按需加载，并保持执行边界。** Claude Code 的 Skills 按需加载正文；DSH 将模型、工具、日志和循环模块化。可借鉴清晰接口与生命周期，而无需复制整套插件生态。[Claude Code Skills](https://code.claude.com/docs/en/skills)、[DSH Architecture](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/architecture.md)

这些是截至审查日读取的公开资料。没有对三款产品执行同题实测，不能宣称 CodeTrail 超越它们；也不能因为某项能力未出现在所读页面，就认定产品不具备该能力。

## 4. 主线亮点：仓库演化下的证据与记忆有效性

建议集中做深一条主线：**同一仓库持续变化时，Agent 能追踪知识、上下文、补丁和测试的有效性，并在跨会话或中断后安全继续。**

原因来自已有基础：源码哈希、记忆版本、原生请求审计、完成门禁、操作意图和独立外验已分别存在。将其连接，比另起一个大系统更容易形成可检查的贡献。

### 4.1 一个完整展示场景

1. 第一会话完成一次实际修复，记录调用关系、环境约束和已执行的验证；提炼候选经验，保留来源。
2. 第二会话处理相关问题，按需召回有效经验与源码证据，展示为何选中、实际注入哪些内容。
3. 修改相关接口或依赖版本。受影响经验失效，旧测试通过状态不能验证当前代码；无关知识在可证明依赖独立时保持可用。
4. 压缩上下文后，Agent 可以按 ID 查回允许读取的原始工具证据，不依赖摘要猜测遗漏内容。
5. 写入之后、记录结果之前终止进程。重启后展示现场与不确定操作，核对并取得新审批后继续，避免重复执行。
6. 外部验证器对最终快照重新验收。回答中每项测试声明能对应真实命令、版本和结果。

这是拟实施的连续场景。当前已有部分机制的离线演示，不能提前宣称真实模型完成全部步骤。

### 4.2 用轻量证据关系实现

```mermaid
flowchart LR
  S[源码块/文件版本] --> M[记忆版本与证据引用]
  M --> R[检索候选及排名]
  R --> C[实际进入请求的上下文]
  C --> E[工具执行与代码变更]
  E --> T[当前快照的测试结果]
  T --> A[最终声明及证据引用]
  S --> I[变更后的有效性检查]
  I --> M
  I --> T
```

关系可先用 SQLite 表和文件对象存储实现，无需上图数据库。每条边记录来源、目标版本和依赖类型。第一阶段使用保守的文件级失效；只有建立可靠符号和依赖解析后，才细化到符号级。不能把启发式调用图当成完整依赖证明。

记忆“来源可验证”与“内容已正确理解”分开。自动 prose 候选可以提炼，但测试通过不能自动证明其中任意文字都正确；验证器只激活其能机械核验的字段，设计原因/偏好等保留明确来源和确认状态。

隐私与权限同样适用：原始证据查回不能暴露秘密、冻结验收金标、参考补丁或隐藏思考正文，不能把日志目录开放为任意文件读取入口。

### 4.3 与 DeepSeek Harness 的关系

DeepSeek Harness 官方定位是基于 Cordis 的通用插件化 Harness，模型适配、工具、日志、循环均可替换。CodeTrail 的拟议方向是一个更窄的仓库演化场景、可解释的证据链，以及可复现的机制对照实验。

这属于工程取舍与验证重点的差异，并非证明 DSH 缺少记忆、验证或恢复能力。单独的向量检索、持久记忆和日志都不是本项目独有创新。应通过组合机制、边界处理和实验展示技术深度。

## 5. 检索升级应如何落地

### 5.1 两类索引分开

- **源码索引**：在 Agent 尚未读过时也可检索；只索引允许访问的工作区内容，函数/方法/文档分块，携带路径、符号、行范围和源哈希。
- **经验记忆索引**：跨会话的事实、决策和流程；携带作用域、来源、版本、确认状态和有效期。

只把“读过的文件摘要”向量化，不能解决首次未知位置定位。向量召回也不能替代权限或证据有效性检查。

### 5.2 最小检索链路

范围/权限检查 → 版本和失效过滤 → 符号/路径匹配、BM25、Embedding 候选 → RRF 秩融合 → 去重 → 上下文预算选择 → 原始源码必要复读。

初期可用 SQLite 保存块、元数据与向量，小规模精确余弦检索即可；有实际容量证据再选 ANN 引擎。Embedding 模型需在实现时核实接口、代码/中文表现、版本、许可证和运行资源，不能猜测模型名或把随机/哈希向量当语义向量。

模型更换、维度、归一化、分块策略改变都必须产生新索引版本。处理空文本、零向量、非有限值、维度不符、删除文件和服务中断；失败回退词法检索时记录降级，不能悄悄填零或混合不同模型空间。

检索 query 应结合当前子目标、实际错误和活动符号，并保留查询来源；不能每轮只用最初用户文本，也不能用金标或参考修复信息构造 query。重排属于可选实验项，先测它的额外延迟和费用。

## 6. 长期记忆应如何落地

按**用途**区分内容，按**生命周期**管理可信度，两者独立：

| 用途 | 示例 | 管理原则 |
|---|---|---|
| 工作状态 | 当前子目标、未完成步骤、最近错误 | 当前任务有效，跨会话恢复时重新核对 |
| 任务经历 | 某次失败、修复和验证过程 | 作为历史事件，历史通过不等于当前通过 |
| 仓库事实 | 接口约定、测试入口、依赖要求 | 绑定来源和适用版本，变更后失效或重验 |
| 可复用流程 | 某类问题的排查步骤、检查单 | 带适用条件、反例和验证记录；按需载入 |
| 用户偏好 | 输出语言、风格偏好 | 明确用户来源与作用域；不能变成安全授权 |

所有内容支持候选、确认、替换、撤销和删除；“长期”指跨会话保存，不能解释为永远正确或永不删除。

统一旧 Markdown 与 SQLite 的读取策略，保留旧数据来源。仓库身份、worktree、分支、版本和会话作用域需显式定义：当前绝对工作区路径绑定较保守，不能直接复制 SQLite 到新路径当作跨工作树共享；共享前必须处理分支版本和授权隔离。

记忆写入应有独立日志，记录为什么写、谁确认、被何证据支持、何时被替换及是否被实际使用。检索命中数不等于产生任务收益。

## 7. 如何证明亮点成立

先写协议与指标，再执行实验。开发集用于选分块/检索参数；冻结后的评估集不用于改参数。既有已调优题不能重新称为未知任务。小规模可接受，但任务数、版本数和重复次数分开报告。

### 检索对照

固定同一源码、候选知识、模型、权限和预算，对比现有词法与混合检索。必要文件/片段金标预先定义；报告候选 Recall@K、最终注入覆盖率、MRR、检索时延、实际 Token 完整性及最终修复验收。排名更好未必能在预算内进入模型，更不等于修复一定成功。

### 纵向记忆验证

使用相关但不同的连续任务及仓库版本序列，分别检验无记忆、现有记忆、升级后的记忆。固定初始状态并明确各阶段允许继承哪些证据，禁止将后续答案写回前置记忆。每个实验工作区重新建立绑定其身份的知识记录，不复制不兼容的数据库。

记录有效知识利用、过期知识采用、错误经验传播、必要源码复读、任务完成和成本。依赖关系金标与“该失效/不该失效”标准必须先冻结。记忆功能关闭/开启的处理不能改变审批或验证标准。

### 恢复与安全专项

在调用前、审批后、执行中、效果已产生但尚未记录等边界注入确定故障。验证重复副作用、未授权执行、遗失状态和恢复后的最终验收。外部不可判断的副作用按 unknown 处理，报告阻塞而非伪造成功。

Prompt Injection、秘密读取、跨工作区污染、检索越界及插件权限测试独立统计，不混入代码修复成功率。

### 现有成绩如何使用

保留历史 30 题与全部运行原始记录，Recall@5 仍沿用对应历史口径。新的纵向记忆实验、检索实验、故障注入和 UI 集成测试各自单列，不能拼成一个更漂亮的成功率。全量软件测试数量也不能充当真实修复任务数。

|---|---|---|
| A：基础语义 | 合法多工具批次、分层规则、取消、usage 未知值、修改冲突保护 | 有正常/拒绝/超时/取消/重启用例；逐调用 ID、权限和最终文件状态一致；全量回归通过 |
| B：统一数据层 | 会话事实源/派生视图定义、记忆迁移策略、证据 ID、源码块索引、混合检索 | 每次召回可解释，变化能正确失效；真实 Embedding 已核验；预算前后证据可追踪 |
| C：亮点闭环 | 经验提炼与核验、原始证据按需查回、持久步骤与恢复、网页证据视图 | 连续仓库演化场景可真实跑通；失败和 unknown 保留；外部验证独立复验 |
| D：受控验证 | 冻结对照协议、真实模型运行、归因与成本报告 | 不选择性报告，效果不佳也保留；任何收益可定位到明确对照条件 |
| E：有限扩展 | 按需 Skill、只读 MCP、结构化 Hooks、有界委派接口完善 | 扩展不增加隐式权限；能卸载/失败隔离；schema、预算、审计与原工具保持一致 |

本轮只完成审查和路线文件，未实施 A–E。该顺序优先解决影响主流程质量的问题，再接入差异化闭环，最后扩展生态；不设未经执行验证的工期或性能承诺。
