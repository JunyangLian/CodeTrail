## 如何从记录复盘

1. 先读 `report.json` 的 status / stop_reason / attempts / tool_steps。
2. 用审计 JSON 中的 trace 行号定位 `model_failed` 或 `tool_executed`，核对参数、错误码和退出码。
3. 对照初始文件、业务规则、最终 diff 和测试哈希；不把模型最终说明视作验收证据。
4. 分开记录症状、可能原因和已确认原因；不知道的根因保留“未确认”。
5. 修复后重跑同一验证命令，说明配置是否改变；明确是否只是同任务重试。

当前归因层：模型请求、模型工具决策、工具执行、输入/业务实现、上下文、环境、持久化/验证器。没有证据时不强行归因于上下文；fixture 自带失败不计作 Harness 崩溃。

## 时长与成本

审计报告汇总三次真实运行时长、尝试次数、工具步数和已解析响应 token。失败请求可能消耗服务资源但没有返回 usage，因此这些值只是已观测用量，不能当总账单。没有受控前后实验，不报告“成本下降百分比”。

## 后续失败统一模板

```text
Task / Repository / Initial State：题目、fixture 哈希、是否为开发任务
配置：模型、协议、超时、预算、提示词/manifest 哈希
观察：退出码、异常、trace 行号
归因：已确认层；尚未确认的可能原因
处理：改了什么，是否同时改变其他因素
验证：同一 verifier、代码差异、测试完整性、全部重试记录
代价：时长、attempts、工具步数、可观测 token 与缺失项
结论边界：是否独立评测、样本规模能支持什么
```
